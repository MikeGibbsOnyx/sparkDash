## 1. Shared weights store — single canonical copies

**Problem confirmed live:** t_15e0a6b7 found *zero* GGUFs >1 GB on any den and per-box scattered weights elsewhere (nyx-den holds DS4-Flash FP8 156G + GLM exl3 166G; creative weights live on iris-den/beast). Drift is already real; four copies is the failure mode.

**Decision (mine, staging allowed; the writes are Mike-GO):**

- **No new hardware, no distributed FS.** At 4×3.7T NVMe with rsync over 200G fabric (~20 GB/s theoretical, >5 GB/s realistic), a **canonical-origin + local-cache** model beats NFS/Lustre/Ceph complexity. YAGNI.
- **Canonical origin: rin-den `/srv/weights` (owner `weights`, group-readable).** Rationale: 2.9T free, idle box, on the fabric. mike-den = designated mirror if rin-den ever gets a resident lane. nyx-den never hosts the store (serving box, disk is KV headroom).
- **Tree convention** (fixed now so nobody invents their own):
  ```
  /srv/weights/<family>/<variant>/   # e.g. deepseek/DS4-Flash-0731-FP8/
      MODEL.sha256        # per-file sha256sums, generated at ingest
      MODEL.toml          # name, family, quant, params, size_bytes, source(HF repo+commit),
                          #   ingested_utc, verified_by, status: candidate|verified|retired
  ```
  Naming: lowercase family, exact upstream variant id, quant suffix. Retire = status change + retention note, never silent delete.
- **Ingest protocol:** download once → `sha256sum` → manifest → `status: verified` → only then may another box rsync it. Consumers rsync to their **local** `/data/models/<same path>` and verify against MODEL.sha256 before first load. No symlinks over the fabric to weights — serving must read local NVMe.
- **Manifest:** `docs/MANIFEST.md` (or generated `receipts/weights-manifest.json`) in the repo listing every `status: verified` model with size + location + last verification date. Regenerated by a cron on rin-den (cheap, local-only, GO-pending).
- **Families in scope:** LTX, PinkCherry, bigLust (creative); Qwen, DS4-Flash, GLM-exl3 (serving); gpt-oss-120b IQ4_XS (layer-split spike payload — nothing exists on disk yet, t_15e0a6b7 confirms).
- **First action when GO'd:** rsync DS4-Flash FP8 + GLM exl3 off nyx-den into the store (frees ~320G on the serving box and gives the pair a verified copy), *after* manifest verification, never before.

## 3. Creative lane contract

**Beast owns video/render when it's up.** It was offline at probe time and is the one box we can't drive — so the contract must not assume it.

- **One endpoint, engine-native — NOT PAIR.** PAIR-EVAL §8 is HOLD and PAIR's routing domain is Ollama/LM Studio only (ComfyUI :8188 is invisible to it). A custom queue endpoint is the only shape that works today.
- **Contract (final):** a thin submission API — `POST /jobs {workflow_json, weights_refs[], priority, lane}` → queue → dispatcher on the render box → artifact lands in `/srv/renders/<lane>/` + receipt comment. Weights referenced **by store path + manifest id**, never bundled per-job (that's how drift is born).
- **Sisters queue, never render locally.** No sister box runs a render while it serves.
- **Fallback when beast is down:** queue holds (renders are latency-tolerant); optional GO'd fallback lane = rin-den Comfy instance for stills only (76G avail at probe, GPU idle) — video stays beast-or-wait until the FLEET-BRAIN §6.3 co-tenancy answer for iris-den lands.
- **Build GO-pending** (new code + new port). Spec-only in this doc; build card: `d3-render-queue`.

| Box | Serving | Render | Training/batch | Rule |

**Time-slicing rules:** (1) serving GPU is non-negotiable during a lane's hours — batch/checkpoint-restartable work only on shared boxes; (2) training on a serving co-tenant is hard-capped via util ceiling, not by convention — enforce with the watchdog, not good intentions; (3) one lane per spare box at a time (rin-den: batch OR spike OR stills); (4) nothing schedules across the fabric until IPv4 lands.
